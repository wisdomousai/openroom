# First-use and tutoring audit — 19 September 2026

## Scope

Fresh local accounts, a complete French B1 lesson and follow-up, all eight authored
French/German A1–B2 lessons, narrow learner screens, keyboard interactions and
automated accessibility checks. A native Chrome walkthrough preceded the repeatable
Playwright journeys. All teaching data in the new journeys is created through the UI.

The local runner starts with empty disposable storage. It uses demo authentication
and the actual local Worker, database, live-session objects and built browser apps.
No hosted database reset was needed. Separate browsers are the accepted substitute
for a physical phone for these functional walkthroughs.

## Problems found and repaired

| Observed failure | Change | Evidence |
| --- | --- | --- |
| Entering a live gap answer could crash the learner page | Read the input value before the deferred React state update | Fill both live gaps, submit, reveal and continue the lesson |
| Gap feedback exposed authoring placeholders | Render the sentence with the learner's submitted words; avoid duplicating the active ballot prompt | Revealed mobile gap screenshot and live answer journey |
| Long French answer labels collided in the presenter | Size chart rows within the remaining chart body and give labels room to wrap | Submitted answers and bounds checks across the sample catalog |
| Narrow learner results squeezed long labels into fixed-height rows | Let the tallest wrapped label determine equal result bands | All sample choice results checked at 320 and 390 pixels, with final screenshots inspected |
| Returning from Notes or the editor lost the student context | Carry the explicit context in return navigation | Review learner work remains reachable after both returns |
| Local sign-in advertised unavailable Google authentication | Describe only configured sign-in choices | Signed-out first-use screen |
| Language students were offered school-year presets | Offer A1–C2 for students/groups; retain school years for classes | B1 selected during UI setup |
| Invalid student forms did not announce their error | Mark the validation message as an alert | Empty-name validation in the journey |
| Presenter keyboard handling interfered with menu dismissal | Let menus and dialogs handle their keys first | Escape keeps the presenter open and restores trigger focus |
| Slide dots had small targets and no tablist arrow navigation | Increase targets and add roving focus with arrows/Home/End | Keyboard slide selection and accessibility scans |
| Participant viewport disabled pinch zoom | Remove the maximum-scale restriction | Automated viewport accessibility check; physical gesture still untested |
| Hovered primary controls lost text contrast | Derive hover colors toward the theme foreground | Full-page accessibility scans |
| Some randomly assigned student badges failed contrast | Use theme foreground initials on a soft palette tint | Full-page accessibility scans, including the formerly failing amber badge pattern |

The audit also corrected two test assumptions: a returning account need not have
the empty-space welcome action, and ranking uses the visible “Send ranking” action.
Neither required changing the product's permissions or introducing an approval step.

## Verified journey

The first-use path is sign-in → tutoring experience → student → learner link → sample
deck → live participant → reading/choice/gaps → private Notes and shared outcome →
homework → practice → private feedback draft → shared correction → correction reused
in a new deck. It preserves the learner credential boundary and verifies that private
Notes, the tutor's next step and unpublished feedback do not appear to the learner.

The catalog rehearsal opens all eight samples through the gallery. It walks their
editor and live slides, submits their questions from a separate learner browser,
reveals actual responses, and saves the authored reading homework through Notes.
It does not simulate a teacher's spoken instruction or prove pedagogical effectiveness.

Fifteen first-use screenshots and axe JSON reports cover full pages with no scan
exclusions. Homework is checked at 320, 390 and 768 CSS pixels. Selected keyboard
paths are asserted directly. This is scoped accessibility evidence, not certification.

## Reproduce and inspect

Build the applications before running the journeys:

```sh
node scripts/verify.mjs --build-only
bun run verify:browser UC-39-first-tutoring-lesson
```

See [UC-39](../journeys/UC-39-first-tutoring-lesson.md) for exact acceptance steps.
The runner records its local configuration boundary in
`e2e/verification-output/run.json`. Playwright writes screenshots and accessibility
JSON to `e2e/test-results/UC-39-*`. This audit's retained copies and verification logs
live under `output/playwright/first-use/`; these generated artifacts are Git-ignored.
All fixture credentials are disposable local values.

## Display and separate-browser follow-up

The tutor and learners now run in separate browser processes. The first-use path
also joins two learners with independent cookies and live connections, submits
different answers, reloads one learner and disconnects/rejoins them while the tutor
advances. Both identities and answers stay distinct. Chromium and WebKit learner
runs both passed the complete first-use path and all eight sample lessons.

New slide masters and all eight tutoring samples use an 8% slide-width content
margin. Split, activity and media layouts honor the saved margin; the freeform
starter and layout presets leave matching breathing room. Existing authored
freeform positions and saved master values are preserved. The editor labels this
setting **Content margin**. Master backgrounds may still extend to the slide edge.

Mobile now opens the authored **Slide** view at the deck's saved ratio. **Reading**
is an explicit option for larger reflowed text. Shared slide typography no longer
inherits line-height, tracking or weight from the surrounding app chrome.

UC-40 compares content, proportional positions, font sizes and bounds across the
editor, control view, actual fullscreen stage and a 390-pixel learner browser for
16:9, 16:10 and 4:3. Its image fixture must load before measurement. See
[UC-40](../journeys/UC-40-slide-display-parity.md) for tolerances and scope; this
does not claim identical geometry for role-specific answer controls or live charts.

Retained evidence for this follow-up lives under
`output/playwright/display-parity/`. The original first-use run above remains a
separate historical result.

## Remaining release acceptance

| Check | Why this run cannot establish it |
| --- | --- |
| Real microphone recording, permissions, speaker/headphone playback and uploaded voice quality | The browser voice regression uses controlled media fixtures |
| Native Safari and a complete screen-reader walkthrough | Automated Chromium/WebKit and selected keyboard paths do not establish these |
| New-user Google OAuth on the release host | Local demo sign-in does not contact Google |
| Teaching with real learners and authentic lesson pacing | The sessions are rehearsals with synthetic learners and answers |
| Native PowerPoint connection, live display and save/reopen | The installed add-in is a separate acceptance track; Office was not automated in this audit |
| Packaged Desktop media and distribution acceptance | Browser success does not resolve the existing native-package failures |
| Paddle sandbox lifecycle and release-host recovery | No payment/provider credentials or hosted environment were exercised |

Physical hardware is a follow-up rather than a blocker for the accepted browser
walkthrough. When available, use the same French B1 path to inspect touch targets,
pinch zoom, soft keyboards, OS background suspension and real audio. The separate
browser checks already cover application reconnect, identity and answer recovery;
they do not establish those hardware/OS behaviors.
